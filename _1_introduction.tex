\section{Introduction}

\label{sec:introduction}

The Samsung Galaxy camera publishes an initial user-visible image, the \emph{draft image}, for each capture and later replaces it with the final image from post-processing.
We call the processing stages that produce the draft image the \emph{draft sequence}.
For selected shot modes, post-processing is deferred until the application enters the background, so the draft image remains the user-visible result throughout the foreground session, making its visual quality more important.
To narrow the draft--final visual gap, we implemented lightweight multi-frame composition in the draft sequence.

However, we have not deployed this feature on any device model because its added processing can violate the \emph{Capture Timeout}, a fixed deadline for producing each draft image whose violation crashes the application by design and blocks the release.
Parallel capture lets the application accept the next shutter input before the preceding draft image is produced, shortening the shot-to-shot interval.
Draft sequences still execute one at a time on a single draft worker, so processing added to one capture also consumes the timeout budget of every capture queued behind it.

We introduced a static thermal guard during pre-release validation to mitigate this risk, but it cannot distinguish safe captures from unsafe ones.
The guard skips the optional stages of the draft sequence once the device's overheat level reaches 4 on a 0--6 scale, but this level reflects neither how long a capture has waited nor how much draft work remains.
Indeed, in our motivating experiment with the guard bypassed, the earliest Capture Timeout at the same starting level varied with resolution, memory pressure, and enabled stages (Section~\ref{sec:guard-limit}).

Workload adaptation and request-release control are established responses to latency and queueing pressure~\cite{approxdet-sensys,timecard-sosp,seda-sosp,breakwater-osdi}.
Our pipeline, however, can neither reject an accepted capture nor preempt a running stage, leaving only two levers: skipping optional stages and delaying the next capture.
These levers carry different user-facing costs.
Skipping optional stages cannot recover time spent waiting, but it leaves the final image unaffected.
Delaying the next capture can prevent waiting, but it lengthens the shot-to-shot interval, a user-perceived cost that is never recovered.
This difference motivates prioritizing responsiveness while retaining optional stages when the remaining timeout budget permits.

We therefore present the Budget-Aware Draft Controller, which coordinates both levers at run time.
A major challenge is that both levers act on draft work not yet executed.
A single Capture Timeout blocks the release, so the controller cannot rely on deadline-miss feedback: underestimation risks a timeout, while overestimation causes needless skips or delays.
The controller therefore estimates stage durations online from completed draft sequences.
\emph{Remaining-Sequence Admission} executes an optional stage when an upper estimate of the remaining draft sequence fits within the capture's remaining timeout budget.
\emph{Capture-Availability Pacing} delays the capture-availability callback, and thus the next capture, when predicted draft work exceeds the remaining timeout budget.

Experimental results on two commercial devices show that the controller enables lightweight multi-frame composition without Capture Timeout.
Across 28 combinations of device, capture condition, and starting overheat level, every controller run completed all 30 captures without Capture Timeout, whereas running every optional stage without the guard timed out in 26 combinations.
In combinations starting at overheat level 4 or higher, where the guard would skip optional stages, lightweight multi-frame composition still executed on an average of 5.2--22.2 of 30 captures per run.
In the production-default 12MP configuration without memory pressure, pacing added no delay during the first five captures at any starting overheat level below 4.
In an ablation at starting overheat level 4, only the full controller completed every capture on time in all three combinations tested.
It also executed optional stages more often than admission alone.
The controller is now undergoing release validation for a forthcoming Galaxy flagship smartphone line.

\smallskip\noindent\textbf{Contributions.}
We summarize our contributions below:
\begin{itemize}[leftmargin=1.2em]
  \item We characterize how serialized draft execution under parallel capture creates a cross-capture deadline problem for lightweight multi-frame composition, and why a static thermal guard does not reflect per-capture deadline safety.
  \item We present the Budget-Aware Draft Controller, which coordinates remaining-sequence admission with capture-availability pacing. To our knowledge, this is the first work to combine these controls in a production camera system under a hard per-capture deadline.
  \item We evaluate the controller on two commercial devices, examining end-to-end effectiveness, component contribution, admission decision quality, and pacing under queue pressure.
\end{itemize}
