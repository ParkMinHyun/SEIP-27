Figure~\ref{fig:controller-overview} illustrates how the \emph{Budget-Aware Draft Controller} coordinates optional-stage execution and capture arrivals to enable lightweight multi-frame composition in draft sequences under per-capture deadlines.
The controller consists of \emph{Remaining-Sequence Admission} and \emph{Capture-Availability Pacing}, which both rely on a shared duration predictor.
Both components use timing estimates derived from runtime observations within the current camera session, without requiring per-device timing tables or thermal-state thresholds.

Algorithm~\ref{alg:overview} specifies where in the capture workflow the controller makes its decisions and updates its state.
For each shutter input \(i\), the workflow sets the deadline \(\mathit{timeout}_i\), where \textsc{TIMEOUT} is the fixed Capture Timeout duration (line~\ref{alg:ov:timeout}).
When the \texttt{captureAvailable} callback is ready for delivery, pacing computes \(\mathit{delay}_i\) from its predicted draft backlog and the draft queue's remaining timeout budget (line~\ref{alg:ov:pacing}).
\textsf{ScheduleCaptureAvailable} schedules the callback for delivery after this delay, exposing the next capture opportunity \(i+1\) to the application (line~\ref{alg:ov:notify}).
The original workflow instead delivers the callback immediately (\(\mathit{delay}_i=0\)).
Although Algorithm~\ref{alg:overview} shows draft processing inline (lines~\ref{alg:ov:configure}--\ref{alg:ov:publish}), each draft sequence is enqueued for the single draft worker, which executes sequences in capture order (Section~\ref{sec:parallel-capture}).
Draft processing therefore proceeds without waiting for \(\mathit{delay}_i\) and can overlap later captures.

At sequence start, \textsf{ConfigureDraftStages} produces the ordered workload sequence \(\mathcal K_i=(k_1,\ldots,k_m)\) (line~\ref{alg:ov:configure}), where each key identifies a stage and its configuration.
The original workflow excludes optional stages from \(\mathcal K_i\) at overheat level~4 or higher; the controller can replace this fixed cutoff with runtime admission.
Before each optional stage \(k_j\), admission compares the estimated duration of the remaining sequence \(\mathcal K_{i,j}=(k_j,\ldots,k_m)\) with the remaining timeout budget \(T_{i,j}\) (line~\ref{alg:ov:admission}).
After the admitted stages execute, \textsf{CompleteDraftSequence} performs the mandatory encoding and saving, represented by the final key \(k_m\), to produce the draft image \(\mathit{draft}_i\) (line~\ref{alg:ov:publish}).

Along with \(\mathit{draft}_i\), \textsf{CompleteDraftSequence} returns the measured durations \(p_i(k)\) of the stages in \(\mathcal K_i\) and the measured draft sequence duration \(C_i\).
The stage durations \(p_i(k)\) update the shared predictor (line~\ref{alg:ov:update}), after which admission and pacing update their states using \(p_i(k)\) and \(C_i\), respectively (lines~\ref{alg:ov:ad-calibrate}--\ref{alg:ov:pa-rebase}).
Pacing accounts for optional stages disabled by admission in the workload estimates used to determine callback delays.

\smallskip\noindent\textbf{Control objective.}
The control objective is to complete each capture's draft sequence before its Capture Timeout deadline and, within that constraint, to weigh capture responsiveness more heavily than optional-stage retention.
Deadline safety comes first because a single Capture Timeout violation blocks the release.
Responsiveness weighs more because added shot-to-shot delay is irreversible, whereas skipping stages lowers draft quality but leaves the final image unaffected.
Let \(\mu_i\) be the time left before capture \(i\)'s deadline at draft completion, \(\delta_i\) the interval between requests \(i-1\) and \(i\), and \(\pi_i\) the interval between their draft completions.
With a fixed timeout duration,
\begin{equation}
  \mu_i=\mu_{i-1}+\delta_i-\pi_i .
  \label{eq:margin-recursion}
\end{equation}
When \(\pi_i>\delta_i\), deadline margin shrinks.
If this persists, the margin is exhausted and the capture violates its Capture Timeout.
Admission can shorten \(\pi_i\) by skipping optional stages but cannot recover time already spent waiting.
Pacing can lengthen \(\delta_{i+1}\) by delaying the next capture opportunity but cannot change work in progress.
Admission acts only on draft work that has not yet executed, and pacing only on capture arrivals still to come.
Yet the optional work that admission retains affects how much delay the next capture needs, so the controller coordinates the two to avoid exhausting the margin.
