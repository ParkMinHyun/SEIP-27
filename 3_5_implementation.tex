\subsection{Framework Integration}
\label{sec:implementation}

The controller integrates at existing framework decision points, preserving the framework's ownership and execution structure without introducing new cross-layer interfaces.
This narrow integration limits cross-component coordination and broad revalidation required for changes to the capture workflow.

\smallskip\noindent\textbf{Framework integration.}
The framework component that already owns the single Draft worker also hosts both modules and the estimator they share, so Draft Sequences continue to execute in capture order on that worker.
Admission replaces the static level-4 thermal guard at the existing admission point and determines whether an optional stage runs at that level.
The integration adds a callback-delivery thread and a watchdog-fallback thread.
On the application-facing \texttt{captureAvailable} path, pacing posts the callback to the callback-delivery thread for release after \(d_i\).

Image processing for an admitted optional stage runs in native code and cannot be cancelled once started.
When the watchdog expires, the watchdog-fallback thread processes a copy of the original input while the in-flight optional-stage processing may continue in parallel.
Resources held by the in-flight processing are released only after it completes, even when the fallback completes earlier.

\smallskip\noindent\textbf{Deployment scope.}
Adaptation uses the configured stage sequence, observed on-device execution times, queue state, and the live Capture Timeout budget.
Shared runtime history derived from observed executions allows both modules to account for device-dependent performance without consuming device-state signals or relying on per-model timing tables or model-specific branches.
Accordingly, the shared decay factor and the two-sequence reserve horizon are the only fixed deployment parameters, while all learned histories and controller state remain scoped to the current camera application session.
The controller is currently being prepared for commercial deployment in a forthcoming Galaxy flagship smartphone line.
For backward compatibility during that rollout, a feature flag allows the controller to be disabled.
When disabled, its estimator is not instantiated, so the framework retains its pre-existing behavior without blocking the Draft pipeline or the next capture opportunity.
