\smallskip\noindent\textbf{Platforms and control configurations.}
The draft sequence's lightweight multi-frame composition targets Portrait mode and requires coordinated support from the HAL and image-processing components.
We evaluate end-to-end binaries incorporating this support on the Galaxy S26 Ultra and Galaxy S26.
Table~\ref{tab:setup} summarizes these platforms and their common run conditions.
To isolate controller behavior, both evaluation binaries bypass the static thermal guard; the Exynos-based Galaxy S26 also bypasses its parallel-capture restriction when either \(M\) or \(S\) is enabled.
Within each experimental condition, all controller configurations use the same production-derived capture implementation and differ only in policy.
Optional-stage skipping and pacing delays therefore reflect controller policy.

\smallskip\noindent\textbf{Workload conditions.}
On each device, we evaluate two operating points: the production-default 12MP configuration under normal memory conditions and a 24MP configuration under memory pressure.
These are the low- and high-load endpoints of the four collected resolution--memory combinations.
We induce memory pressure by running AnTuTu Benchmark~11.1.4 alongside the camera application.
The 24MP condition denotes the requested capture mode; at overheat level~5 and above, the production camera stack falls back to 12MP.

\smallskip\noindent\textbf{Run protocol.}
We first reach each target starting overheat level through repeated captures or idle cooling.
We then force-stop and relaunch the camera application to reset process-local controller state, and begin the run when the device reports that level.
Thermal state then evolves without external intervention.
A reproducible ADB loop issues each shutter input as soon as the application receives \texttt{captureAvailable}, saturating the exposed request rate.
Each run targets 30 consecutive captures and terminates at the first Capture Timeout.
