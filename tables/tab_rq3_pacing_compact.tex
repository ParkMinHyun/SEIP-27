% Compact coordination-aware RQ3 main-paper table.  The original RQ3 policy,
% selectivity, and calibration tables remain untouched as historical
% alternatives; see docs/rq3-current.md, which is the authoritative handoff for
% this pair and the source of every claim limit recorded below.
%
% Sources:
%   data/rq3/policy/summary.csv
%   data/rq3/coordination/summary.csv
%   data/rq3/coordination/action_summary.csv
%
% ---------------------------------------------------------------------------
% Naming, and why it changed
% ---------------------------------------------------------------------------
% Every printed label now uses a term the manuscript already prints elsewhere.
% The generated CSVs and scripts/rq3_coordination_*.py keep their own column
% names, so this is the map between the two vocabularies:
%
%   printed here                 elsewhere in the repository
%   -----------------------------------------------------------------------
%   pacing decision              transition (one shot-to-shot interval; a
%                                30-capture run holds 29 of them, which is the
%                                denominator of "Activated (%)" in
%                                Table~\ref{tab:rq1_controller_behavior})
%   run                          burst; a complete 30-capture session, the unit
%                                counted by "Survived runs" in RQ1(a)/(b)
%   budget left                  spare (retrospective pressure, negated)
%   required delay               envelope, d*
%   missing delay                d* - d: potential avoided delay (flexible
%                                band), shortfall_ms (mandatory block)
%   skipped optional work        demotion (Bokeh+Filter -> Filter only ->
%                                Encoding only), which RQ2 prints as "Skipped"
%   deadline margin              realized margin; RQ1(a) prints the normalized
%                                form as "Slack P5"
%   this / next Draft            target / next
%
% ---------------------------------------------------------------------------
% Layout, and why it is the repository's and not booktabs
% ---------------------------------------------------------------------------
% Every other table in this paper is ruled on both axes, sized to \columnwidth by
% \fittabcolsep, and groups its rows under full-width bold headers.  An earlier
% revision of this table used \toprule/\midrule with no vertical rules and fixed
% p{0.50\columnwidth} columns; it read as a foreign object beside Tables II--IV
% and stopped short of the column edge.  Keep the house form.
%
% Every row label is one line.  In an earlier revision about half of them wrapped
% -- the two activation rows and the two floor-miss \makecell stacks -- which left
% the metric column ragged and doubled the table's height.  Symbols survive only
% where they carry the definition: the two required-delay formulas sit in the
% group header, not in a cell.  Any new label has to be checked against the
% 128pt metric column at \scriptsize before it is committed.
%
% The 12MP column prints "--" on the four floor-miss rows because no 12MP pacing
% decision fell below the mandatory floor.  That is a real zero, not a missing
% measurement, and the "Decisions below the mandatory floor" row directly above
% states it as 0 of 79.
%
% ---------------------------------------------------------------------------
% What moved off the page, and what still has to come back
% ---------------------------------------------------------------------------
% An earlier revision carried a twenty-line \tiny note block under the tabular.
% It held the definitions, the horizon argument, and the claim limits, and it was
% taller than several of the row groups.  The repository convention is that this
% material lives in the .tex header and in body text; the definitions are
% therefore recorded below.
%
% NOT YET WRITTEN: Section~\ref{sec:experiments} has no RQ3 prose, so the claim
% limits below currently appear nowhere a reader sees them.  They must be in body
% text before submission.  The three that cannot be dropped are marked LIMIT.
%
% Definitions
%   B          measured Draft backlog at the pacing decision
%   T          budget left in the deadline window at the decision
%   C_exec     realized duration of the admitted Draft sequence
%   C_mand     the mandatory part of C_exec: DynamicFunction, Encoding and
%              measured Draft overhead, i.e. C_exec with the optional work that
%              admission can skip removed
%   d          the applied pacing delay
%   d*_exec    ceil( [B + 2*C_exec - max(0,T)]^+ / 2 ), the delay the realized
%              Draft work required
%   d*_mand    the same on C_mand: the mandatory floor
%   budget left after the queued Draft work
%              max(0,T) - (B + 2C), as a share of the Capture Timeout budget.
%              A negative value is a projected overrun reconstructed after the
%              run, NOT an observed Capture Timeout.
%   no budget left
%              STRICTLY negative, i.e. a projected overrun, which makes it the
%              same set as "Decisions that required a delay": d*_exec is
%              ceil(pressure/2), so a decision at exactly zero budget left needs
%              no delay.  Both are 79 and 140, and the halves add up: 61+18 and
%              97+43.  An earlier revision took the population from the
%              half-open [0, inf) pressure BAND of the historical selectivity
%              exhibit and printed 141 here against 140 four rows down, a
%              one-decision disagreement (24MP run 2#27 capture 28, pressure
%              0.0 ms) that read as an arithmetic error.  The bands are
%              unchanged; scripts/rq3_policy_metrics.py now carries a separate
%              strict cut, OVERRUN_PCT, for everything this table prints.
%   skipped optional work
%              admission ran less than Bokeh+Filter, i.e. Filter only or
%              Encoding only
%
% ---------------------------------------------------------------------------
% Units, and the rule that decides them
% ---------------------------------------------------------------------------
% The Capture Timeout budget is an internal constant and must not be recoverable
% from the manuscript.  It becomes recoverable the moment one quantity is printed
% BOTH as an absolute duration and as a share of the budget, so the rule is per
% quantity, not per table: each one appears in exactly one unit across the whole
% paper.
%
%   delay -- applied, not applied, and the excess over what was required
%       Milliseconds.  Table~\ref{tab:rq1_controller_behavior} and
%       Table~\ref{tab:rq1_ablation} already print the applied delay in ms, and
%       it is the one number a product owner reads directly.  So the rows here
%       are ms too: "left to admission", "Applied minus required" and "Per paced
%       capture".  Printing any of them as a share of the budget would divide
%       straight into RQ1's milliseconds.
%   deadline margin
%       Share of the budget.  RQ1(a) already prints the normalized form as
%       "Slack P5 (%)", so ms here would be the same mistake in the other
%       direction.
%   wait for the Draft worker
%       Share of the budget.  It has no millisecond counterpart anywhere in the
%       manuscript, and the share is the more informative form: the median wait
%       is 73.4% of the whole budget, which is the reason the online backlog
%       estimate is stale by the time the Draft runs.
%   budget left, and everything the figure plots
%       Share of the budget, for the same reason.
%
% Before adding a row, check which unit the quantity already uses elsewhere; do
% not introduce a second one for it.
%
% The 2C horizon is the deployed prospective model: (i) the Draft that begins
% after the pacing decision and (ii) the Draft of the next capture released by
% that delay.  Waiting one millisecond both drains one millisecond of backlog and
% shifts the next deadline by one millisecond, hence the division by two.
%
% The two rows a reviewer reaches for first, and why they are here
% ---------------------------------------------------------------------------
% "Paced although no delay was required" and the "Applied minus required" block
% close the one gap this table used to have: it reported only the side where
% pacing fell short of the requirement (the missing-delay row) and never the side
% where it exceeded it, which is the larger of the two on this data.  Reporting
% one tail of a two-tailed question reads as selective, and the numbers are easy
% to derive from the rest of the table anyway: 411 paced minus the 61 paced
% decisions inside the 79 that required a delay leaves 350, and likewise 374 of
% 471 in 24MP.  State it rather than let a reviewer compute it.
%
% Neither row is a defect on its own.  A preventive controller is supposed to act
% before the projection reaches the deadline; d*_exec is a lower bound on what
% was required, reconstructed after the run, not a set point the controller aims
% at.  What would be a defect is claiming an appropriately sized delay while
% leaving four fifths of the pacing outside the analysis.
%
% The decomposition is exact away from the max(0,.) clip -- on decisions where
% both d > 0 and d* > 0,
%
%   d - d*  =  (Chat - C)  +  (Bhat - B)/2
%
% identically, verified in tables/tab_rq3_pacing_calibration.tex at residual mean
% 0.00 ms.  The Draft-duration estimate carries essentially all of it (+302 and
% +445 ms) while the backlog estimate is an order of magnitude smaller and
% usually slightly optimistic (-30 and -60 ms).  The cause is by construction:
% CaptureAvailablePacingSession.getMaxDraftSequenceDurationMs prices Chat at the
% run's observed MAXIMUM Draft duration for the capture's size bucket, so a
% max-based estimate against a typical realized duration necessarily over-covers.
% That is the sentence the body text needs; it turns the over-shoot from an
% unexplained excess into a documented design choice with a measured price.
%
% Populations differ between the parent row and its two children and the labels
% cannot carry that: the P50 surplus is over paced decisions (411 and 471), while
% the two terms are over the paced decisions that also carried a requirement
% (61 and 97), which is the subset where the identity holds without the clip.
% Source: data/rq3/calibration/summary.csv, the "All" band of each condition.
%
% ---------------------------------------------------------------------------
% Derived quantities
%   missing delay     d* - d, the part of the required delay that was not
%                     applied.  Against d*_exec inside the admission-flexible
%                     band, against d*_mand in the mandatory-floor block.
%                     Figure~\ref{fig:rq3_pacing_compact} plots twice this
%                     quantity, because one millisecond of waiting buys two of
%                     budget; see that file's header for the identity that makes
%                     its diagonal the deadline.
%                     LIMIT: this is not a counterfactual end-to-end speedup.
%                     Pacing is closed-loop, so a smaller delay would have
%                     changed later arrivals, backlog, admission and thermal
%                     state.
%   backlog overlap   sum(min(d,B)) / sum(d) over paced decisions
%   per-run cost      sum(d) divided by the sum of shot-to-shot intervals
%   P50 / P95         inclusive percentiles
%
% LIMIT -- this Draft or the next.  The flexible-band skip rows report whether
% admission skipped optional work on the Draft attached to the pacing decision
% or on the next capture's Draft, which is the same two-Draft horizon the delay
% is sized against.  It is an observed-action audit over that horizon and must
% never be phrased as causal attribution of the next admission decision to the
% current delay.  The generated CSVs call these two columns target and
% targetOrNext.
%
% LIMIT -- the mandatory floor.  d*_mand is a sufficient reservation condition
% reconstructed after the run, not the timeout boundary.  All 14 floor misses had
% optional work skipped on their own Draft, but because d*_mand already excludes
% optional work, that skip documents coordination rather than erasing the
% deficit.  The 14 cluster in four 24MP runs, retained at least 307 ms (this
% Draft) and 276 ms (next) of deadline margin, and none produced an actual
% Capture Timeout.  Backlog under-estimation in 14/14 and rising headroom in
% 12/14 over a median 4.78 s of queue residence are observationally consistent
% with queue and thermal drift after the online decision; do not claim causality
% from this trace split.
%
% Population.  Records affected by the known timeout-measurement error were
% removed as invalid observations, which is data-quality filtering and NOT
% outcome-based survival conditioning; no valid analyzed run experienced an actual
% Capture Timeout, and the manuscript must not describe this population as
% survival-conditioned.  Watchdog-truncated decisions lack a complete realized
% Draft duration and are excluded from the required-delay reconstruction only.
% Complete 30-capture runs from
% data/ablation_sampling/48U_metrics_{12MP_normal,24MP_memory}_0803_{1,2}.xlsx:
% 70 and 69 runs, 1,920 and 1,861 analyzed pacing decisions.
%
% Regenerate with scripts/rq3_policy_metrics.py, scripts/rq3_coordination_metrics.py
% and scripts/rq3_coordination_audit.py; see docs/rq3-current.md for the order.
