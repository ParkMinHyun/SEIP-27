% RQ3: does pacing intervene near the deadline, is the delay it applies the right
% size for what admission left behind, and what does that cost?
%
% Companion to Figure~\ref{fig:rq3_pacing_policy}.  Read the header of that file
% for the panel-by-panel reasoning; this one carries the population, the
% definitions, the provenance and the limits.
%
% ---------------------------------------------------------------------------
% Why this pair exists beside the selectivity pair
% ---------------------------------------------------------------------------
% Table~\ref{tab:rq3_pacing_selectivity} establishes that the pacer fires
% selectively and prices the intervention.  It does not answer either half of
% RQ3's actual question -- whether the delay is the right SIZE for the Draft
% backlog and the remaining Capture Timeout budget -- and it cannot explain its
% own two boundary mismatches.  This table adds both:
%
%   1. Boundary diagnosis.  Of 3,781 analyzed transitions, 15 were paced although
%      the retrospective trace later showed more than 40% of the budget spare,
%      and 62 projected an overrun retrospectively yet received no delay.  Both
%      groups are diagnosed here against the controller's own estimation error.
%   2. Admission-aware sizing.  d is the least integer delay that closes the
%      predicted deficit under the deployed two-Draft model, computed on the
%      sequence admission actually selected.  The table reports that the recorded
%      delay matched that minimum on every transition, and that the wait is spent
%      draining outstanding work rather than idling.
%
% The first and third groups below overlap the selectivity pair on purpose so that
% the new pair can stand alone.  The two pairs are alternatives, not complements.
%
% ---------------------------------------------------------------------------
% Structure, and why it is not the sibling table's
% ---------------------------------------------------------------------------
% Three claim groups in the order a reader asks them -- where the delay lands, how
% it is sized, what it costs -- and then the exceptions.  Row labels are words
% rather than symbols wherever a word will do, because a reader meeting
% Bhat - B for the first time in a table cell has to leave the table to decode it.
%
% The boundary group re-labels the two value columns.  Both mismatch classes are
% pooled over conditions -- they hold 15 and 62 cases, and a rate over 6 of them
% would not be a summary of anything -- which leaves the two columns free, and
% putting the classes in them turns nine separate rows into nine contrasts: +29.4
% against -15.3 points of backlog error, 1.61 s against 5.14 s of queue residence,
% 4 of 14 against 53 of 62 on thermal drift.  The mechanisms are different, and
% the layout is what makes that legible rather than something the reader has to
% assemble from two paragraphs.
%
% An earlier revision ran the two classes down the rows with the conditions across
% the columns, repeating each pooled value across both cells.  It printed one
% number twice and read as two independent measurements; do not restore it.
%
% Dropped from that revision, because Figure~\ref{fig:rq3_pacing_policy} carries
% them better: the 20--40% spare band (panel a), the delay as a share of the
% backlog it drains (panel c reads the two quantities directly), and the
% thermal-status and overheat-level counterparts to the headroom row (the headroom
% row is the one that matters, and the reason is in "What the numbers say" below).
%
% ---------------------------------------------------------------------------
% DISCLOSURE -- what keeps the Capture Timeout budget out of the exhibits
% ---------------------------------------------------------------------------
% Every RQ3 exhibit keeps risk quantities in shares of the budget and never in
% milliseconds, so that no rendered cell, axis or caption discloses the budget;
% docs/rq1-rq3-metrics-guide.md states the rule for captureTimeoutMs.  Recovering
% the budget takes one quantity in both a budget-relative and an absolute form, so
% the rule is really a rule about pairs.
%
% This pair is internally clean, and two choices are what make it so:
%
%   - The backlog estimation error is in points of budget in both the table and
%     panel (b), and the backlog never appears as a percentage of the budget
%     anywhere in this pair.
%   - Panel (c) plots the delay and the backlog in SECONDS, not in points of
%     budget, precisely because the cost group below prints the delay in
%     milliseconds.  A budget-relative delay beside a millisecond one is a
%     one-step division; two absolute forms of the same quantity are not.
%
% What is NOT clean is shipping this table together with
% Table~\ref{tab:rq3_pacing_selectivity}.  That table prints the measured backlog
% as a percentage of the budget (P50 52.5 paced), and this one prints the applied
% delay in milliseconds (P50 381) while panel (c) shows the backlog in seconds
% against it; the median backlog read off panel (c) divided by 52.5% recovers the
% budget to within a percent.  Retiring the selectivity pair, which is the intent
% of this pair, removes the disclosing term.  Keeping both means dropping either
% this table's millisecond row or that table's backlog percentages.
%
% ---------------------------------------------------------------------------
% Definitions
% ---------------------------------------------------------------------------
%   B           measured backlog at the pacing decision (RQ3Pacing.realBacklogMs)
%   C           realized duration of the admitted Draft sequence
%   T           window left on the newest committed capture's deadline
%   Bhat        the controller's backlog estimate at the decision
%   Chat_adm    reserved duration of the sequence admission selected, i.e. the
%               post-admission reserve rather than the reserve of the sequence
%               originally planned
%   retrospective pressure   B + 2C - max(0,T), as a share of the budget.
%               Negative is spare time.  At zero the queue plus the next two
%               Drafts are projected to exhaust the budget exactly.  "Spare" in
%               the first group is this quantity negated.
%   safe, yet paced        pressure < -40% of budget with d > 0
%   overrun, yet unpaced   pressure >= 0 with d = 0
%   demotion    the executed sequence's optional-work class ranks below the
%               planned class, on Bokeh+Filter > Filter only > Encoding only
%   queued-ahead work      the Draft sequences of the same burst that end after
%               the decision and start before the target's own Draft
%
% Every estimation-error row is signed the same way, estimate minus realized, so
% a positive number always means the controller reserved more than it turned out
% to need.  Two of the source quantities are recorded with the opposite sense
% (realized minus reserved) and are negated here; the CSV keeps the recorded sign.
%
% Bracketed counts in the first group are the band populations the rate is taken
% over.  The corresponding 95% intervals are drawn as whiskers in
% Figure~\ref{fig:rq3_pacing_policy}(a) and are not repeated here.
%
% ---------------------------------------------------------------------------
% What the numbers say
% ---------------------------------------------------------------------------
% Selectivity is a threshold claim on this table, not a shape claim.  Activation
% is 1.4 and 1.0% while more than 40% of the budget is projected to remain spare,
% about half in the last fifth, and 77.2 and 68.8% once the projection reaches the
% deadline.  The pooled rates of 21.4 and 25.3% are the mean of a policy that is
% idle in a quarter of the bursts and active in half the captures of the worst
% ones, and must not be read as "the controller delays one capture in four".
%
% Safe, yet paced: 15 cases, 1.2% of the loosest band, and the mechanism is an
% admission-demotion cascade.  All 15 target sequences were demoted by admission
% and 55 of 58 queued-ahead tasks were demoted with them, so the reservations the
% pacing decision carried had been priced before the shorter realized sequences
% drained the queue.  The backlog estimate was conservative in 15 of 15 cases by a
% median 29.4 points of budget, the target's own reserve by a median 1.03 s, and
% the queued-ahead reserves by a median 3.53 s in aggregate.  Thermal headroom was
% flat across the decision-to-execution interval (rose in 4 of 14 comparable
% cases, median delta zero), so thermal drift is not this group's explanation.
%
% These are NOT to be called false positives without qualification.  The online
% controller did not have the realized durations the retrospective diagnostic
% uses; it paced against the work it had been told to expect.
%
% Overrun, yet unpaced: 62 cases, 28.2% of the overrun band, and the mechanism is
% queue-residence backlog underestimation.  The backlog was under-estimated in 61
% of 62 cases by a median 15.3 points of budget, and the crossings are shallow --
% 55 of 62 within 10 points of budget of the projection.  The target waited a
% median 5.14 s between the pacing decision and its own Draft execution, against
% 1.61 s in the other group.  Over that residence, thermal headroom rose in 53 of
% 62 cases (median delta 0.010) while the coarser thermal status rose in only 17
% and the overheat level in 8, which is why headroom is the field the table
% reports: it reacts earlier and therefore exposes drift the levels hide.
% Queued-ahead work overran its aggregate reserve by a median 336 ms while the
% target sequence's own reserve was calibrated to a median 11 ms, so the mismatch
% belongs to stale reservations for work ahead of the target rather than to a
% large error on the target Draft itself.  Demotion is not this group's story:
% only 29 of 62 targets and 64 of 396 queued-ahead tasks were demoted at all.
%
% Say "associated with" or "consistent with", never "caused by".  The
% decision-time thermal value is a trace-derived proxy -- the thermal snapshot of
% the most recently started Draft sequence at the decision timestamp -- and this
% is an observational split of recorded traces, not a controlled replay that fixes
% the arrival stream and varies only thermal state.
%
% Admission-aware sizing.  Waiting d milliseconds does two things at once: it
% drains d milliseconds of outstanding backlog and it shifts the next capture's
% deadline by d milliseconds, so the residual predicted deficit falls by 2d and
% ceil(deficit/2) is the least integer delay that closes it under the deployed
% two-Draft model.  The recorded delay matched that value on 3,781 of 3,781
% transitions.  Because Chat_adm is the reserve of the sequence admission
% selected, the delay does not repay optional work that admission already removed.
%
% What this establishes, and what it does not.  Established: the delay is minimal
% with respect to the post-admission predicted deficit, and it is empirically
% work-conserving -- 100.0 and 98.7% of applied delay overlapped outstanding
% backlog, and only 0 and 8 waits outlasted it.  NOT established: that admission
% saved a specific amount of delay relative to pacing the sequence originally
% planned.  That needs a shadow Chat_full and the counterfactual d_full for every
% decision, and neither is recorded.  Do not write "globally optimal" or "optimal
% under every counterfactual".
%
% ---------------------------------------------------------------------------
% Population and provenance
% ---------------------------------------------------------------------------
% Source: data/ablation_sampling/48U_metrics_12MP_normal_0803_{1,2}.xlsx and
% 48U_metrics_24MP_memory_0803_{1,2}.xlsx (ML implementation commit 99aae0a,
% exported by CaptureMetricsExcelExporter), both arms with admission and pacing
% enabled.  Run and transition eligibility are identical to
% Table~\ref{tab:rq3_pacing_selectivity} and are documented there: 70 and 69
% eligible bursts, 1,920 and 1,861 analyzed transitions, and the same two limits
% -- the population is survival-conditioned because the export filtered the
% Capture-Timeout sessions out, and the 12MP thermal rows carry the RQ1(a)
% balancing-trim bias.  Both limits apply here unchanged.
%
% Regenerate every number with scripts/rq3_policy_metrics.py, which writes
% data/rq3/policy/ and prints each value quoted above and in
% figures/fig_rq3_pacing_policy.tex.  It imports the loader from
% scripts/rq3_calibration_metrics.py and the binning, cluster bootstrap and ECDF
% from scripts/rq3_selectivity_metrics.py rather than reimplementing any of them,
% so the populations here are the sibling exhibits' populations by construction
% and the band intervals are the same numbers, not merely compatible ones.
% summary.csv holds every cell printed below; boundary_case_details.csv holds the
% 77 auditable boundary cases.
%
% One definition in that script does not come from the loader and must not be
% swapped for the loader's.  Demotion here is a drop in the executed sequence's
% optional-work class.  load() carries a 'demoted' field that instead compares the
% two workload keys for equality, and the keys also differ on watermark and
% image-format changes that remove no optional work; the two definitions disagree
% on 19 of the 3,781 analyzed transitions.  The rank form is the one that supports
% the demotion-cascade reading, so the script computes it and ignores load()'s
% field.
%
% One limit on the queued-ahead reconstruction: it is built over the analyzed
% transitions of each burst, so Draft work belonging to shots 1--2 or to a
% watchdog-dropped capture is invisible to it.  The queued-ahead counts are lower
% bounds for that reason.
