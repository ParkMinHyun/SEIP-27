% RQ2: anatomy of the eight unsafe fresh-model admits.
%
% Built per section 5.4 of docs/rq1-rq3-metrics-guide.md from the workbooks
% below (ML implementation commit c871d3a); same decision set as the
% unsafe-admit cell of Table~\ref{tab:rq2_admission_audit}.  Rows are ordered
% by growth factor within each optional-work group, so the labels are
% positional.  Regenerate with data/rq2_spike_anatomy.mjs in the ML repository.
%
%   A = 48U_metrics_12MP_normal_0729_PacingOnly_1.xlsx
%   B = 48U_metrics_24MP_memory_0729_PacingOnly_1.xlsx
%   C = 48U_metrics_24MP_memory_0729_PacingOnly_2.xlsx
%
% The baseline is the IMMEDIATELY PRECEDING capture of the same run and the
% same optional-work group, not an average over three recent safe decisions.
% The predicted bound is formed from what the controller had just observed, so
% the fair question is whether the one shot before the spike gave any warning.
% In all eight cases that preceding capture was itself a safe admit, so the
% baseline is not contaminated by an earlier overrun.
%
%   id  book run shot     B   Cprev      C      UB  growth  overrun
%   M1    A   30   21  1516   877.0   2033   903.8   2.32      517
%   M2    A   11    9  1308  1216.0   2367  1229.1   1.95     1059
%   M3    A    9   26  1749  1221.0   2357  1222.5   1.93      608
%   M4    A   31   29   746   596.0    777   682.8   1.30       31
%   M5    C   18   20   844   747.0    855   765.1   1.14       11
%   S1    C    6   11   975   611.0    979   915.0   1.60        4
%   S2    B   29   14   653   501.0    713   593.0   1.42       60
%   S3    C   18   20   472   415.0    483   467.7   1.16       11
%
% For M2 and M3 the predicted bound and the preceding capture's measured cost
% differ by 0.010 and 0.001 of the budget, so the model's inputs carried no
% warning at all before a roughly 2x jump.
%
% Panels (b) and (c) plot the two measured quantities whose quotient is the
% latency in panel (a).  Over the node suffix, CPU work is sum(cpuTimeMs) and
% the cores serving it is sum(cpuTimeMs) / sum(wallTimeMs), both read from the
% per-node sheets rather than AdmissionReplay, which omits nodes that carry no
% admission decision.  Node wall time then satisfies
%
%   wall = CPU work / cores
%
% identically, and covers 97.5 to 99.0 percent of the panel (a) latency C, so
% the two panels account for essentially all of the increase.
%
%   id   cpu_p   cpu_e  factor   cores_p  cores_e  factor   wall_p  wall_e  factor
%   M1    1687    2379   1.410      1.96     1.18   0.603      859    2009   2.339
%   M2    2411    2775   1.151      2.03     1.19   0.585     1186    2335   1.969
%   M3    2472    3340   1.351      2.08     1.44   0.694     1191    2318   1.946
%   M4     948    1043   1.100      1.62     1.37   0.848      586     760   1.297
%   M5     849    1044   1.230      1.16     1.24   1.076      734     839   1.143
%   S1     863    1067   1.236      1.44     1.10   0.764      599     969   1.618
%   S2     968    1324   1.368      1.98     1.91   0.962      489     695   1.421
%   S3     375     560   1.493      0.92     1.18   1.282      407     474   1.165
%
% An equivalent additive split of wall_e - wall_p, kept for the prose and
% deliberately not plotted because it reads as a derived quantity rather than a
% measurement: cpuTerm = (cpu_e - cpu_p) / cores_p and
% coreTerm = cpu_e * (1/cores_e - 1/cores_p), summing exactly to the increase.
%   M1 +352/+798 = +1150   M5 +169/-64  = +105
%   M2 +179/+970 = +1149   S1 +142/+228 = +370
%   M3 +418/+709 = +1127   S2 +180/+26  = +206
%   M4  +59/+115 =  +174   S3 +201/-134 =  +67
%
% Control signals recomputed against the same preceding capture.  Blocking GC
% time was 0 ms for every baseline and every event, and overheat level and
% thermal status were identical in all eight.  Run-queue wait and nonvoluntary
% context switches moved in both directions:
%   M1 rq 18->32  cs 108->119      M5 rq 94->70   cs 255->150
%   M2 rq 59->88  cs 222->228      S1 rq 87->227  cs 311->463
%   M3 rq 55->47  cs 196->131      S2 rq 23->87   cs  68->168
%   M4 rq  5->2   cs  37->27       S3 rq 83->58   cs 224->141

% Layout: one panel per row, each spanning the column, so the eight rows get
% the full width instead of a third of it.  All three panels share the same row
% order and the same previous/this-capture grammar, so one key serves them all
% and no legend box sits inside a plot.

  \caption{Anatomy of the eight unsafe admits the always-admit model would have
  produced, each compared with the capture immediately before it in the same
  run and optional-work group.  (a) Remaining-sequence latency normalized by
  the admission budget; every event lands past $1.0$, and for M2 and M3 the
  predicted bound sits on the preceding capture, so the model's inputs carried
  no warning before a roughly twofold jump.  The predicted bound applies to (a)
  only.  (b) and (c) give the two measured quantities whose quotient is that
  latency: the CPU time the remaining work consumed, and how many cores served
  it in parallel.  The work grew moderately in all eight cases ($\times1.10$ to
  $\times1.49$), whereas the three largest spikes lost close to half their
  parallelism ($\times0.60$, $\times0.59$, $\times0.69$); M5 and S3 instead
  gained parallelism, which is why their latency barely moved.  Contention for
  the cores, not a larger workload, is therefore what the admission model
  failed to anticipate.}
